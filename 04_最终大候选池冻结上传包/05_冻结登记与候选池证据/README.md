# 最终冻结研究包与候选池证据

这个目录是 `04_最终大候选池冻结上传包` 下的统一研究证据入口，集中保存“最终四个信号是怎样从大候选池中确定下来”的研究证据、冻结登记和上传包路径索引。

它和 `01_基础三状态与统一六列运行` 是两个不同任务：

- `01_基础三状态与统一六列运行` 是运行包。远端只读取现货和随包的冻结源码/参数，直接生成六列表，不重建候选池，也不做候选遍历。
- 本目录是研究证据包。它保存候选池规模、最终 Top1、Development/Validation/Test 流程、冻结文件和历史逐日审计结果，供研究复核和汇报时解释。
- `../../05_上传包_日期解析修正版` 是此前的候选池/冻结验证工程包，保留了非零和极端信号的源码、冻结产物及远端运行记录；本目录把关键材料复制出来，避免需要到多个目录里寻找。
- `../../01_报告资料与基础上传包/基础上传包_远端九列重建` 是旧的九列表重建/基线包，里面的 `1545` 和 `长0` 只作为历史基线和审计依据，不属于当前六列最终输出的四个信号。

## 推荐阅读顺序

1. 先看 `01_当前四信号冻结登记/研究流程确认.md`，确认研究流程、数据口径和 Test 的角色。
2. 再看 `01_当前四信号冻结登记/当前四信号冻结参数登记表.json`，查看四个信号的版本、阈值、候选 ID 和候选池规模。
3. 非零退出候选池看 `02_候选池冻结证据副本/1545_rq_run_company_sides.json`；其中记录了每个版本的 2,592 候选、两侧总候选数、去重后的信号数、最终 Top1 和各阶段指标。
4. 大涨/大跌候选池看 `02_候选池冻结证据副本/paper_engine.py`、`extreme_engine.py`、`company_pool_runner.py` 和两个 `FROZEN_*` 文件。这里同时明确了研究阶段的 `4096 base × 12 coverage = 49,152` 组合，以及运行阶段只算冻结候选的逻辑。
5. 最后看 `03_原始研究统计表/`，这是报告构建使用的基础统计表副本。

## 研究流程结论

当前登记的最终四个信号遵守以下流程：

1. Development（2018–2022）用于拟合、校准阈值和初步筛选。
2. Validation（2023–2024）用于在未参与拟合的时间段做冻结前筛选和稳定性门槛。
3. 选出最终版本后冻结参数。
4. Test（2025–最新）只用于冻结后的观察和报告，不参与重新选候选、调阈值、回写参数或更新候选池。

因此，`01_基础三状态与统一六列运行` 的正确运行方式是“现货更新后直接重算冻结版本”，而不是再次运行大候选池。若需要研究复核候选池，应查看本目录和 `../../05_上传包_日期解析修正版`，不要把候选重建加入日常更新流程。

## 一个需要保留的审计说明

V189 的 `paper_metadata.json` 明确登记了 49,152 个候选。V156 的历史元数据条目仍保留了 `paper8: 8×8×8×8 base × 12 coverage` 的网格定义，但 `candidate_count_per_side` 字段没有同步填入，状态字段也仍是旧的保留值。代码实际使用四个 8 级轴和 12 个覆盖率，因此候选池规模按 `4,096 × 12 = 49,152` 记录，并在登记表中明确标注了这个元数据不一致，避免把它误写成“已经有完整的 V156 序列化排行榜”。

这不影响当前冻结运行：V156 的最终冻结候选、阈值和冻结前后 Test 只观察记录都已经存在；它只说明如果以后要复现“完整 V156 候选排行榜”，应重新运行研究阶段候选池审计，而不能把当前快速上传包当成候选池重建包。
